# 重建边界与顺序

## 已确认的产品范围

- 仅服务主人本人；保留访问保护，不建立注册、用户管理和租户隔离体系。
- PC 优先，移动端保证阅读；删除专门的拍照入口。
- 资料采集、解析、管理、自然语言搜索、带来源的多轮问答、任务与调用追踪。
- 财务资料管理和统计属于 cardless；本系统未来只读调用其 API。

## 本次清理

移除旧的“Claude 提取财务字段 → 一份文件一个向量 → Chroma + PostgreSQL”链路，
以及依赖该链路的业务 API、页面、CLI 命令和测试。
移除多用户数据库访问、注册、体验账户、历史 schema 初始化与手动迁移脚本。
移除 Chroma、Redis、Celery、SentenceTransformer 和 Anthropic 的运行依赖。
保留 React/Vite、FastAPI、PostgreSQL、同源 nginx 入口和基础访问认证。
第一版 MVP 不引入 worker、任务队列或后台任务框架，文档处理在请求内顺序执行。

清理之后已加入文档 MVP：上传、原件保存、解析、分块、查看和手动重试。
这是新实现，不是旧功能兼容版本。pgvector、embedding 和问答模型尚未接入。
原件和已有数据库未改动，部署时也不自动删除旧卷、旧表或导入旧用户的数据。
旧系统最近完整版本可从 Git 提交 `24792fb` 查阅。

## 业务模块逐步加入

1. **文档与同步处理（已实现 MVP）**：独立 schema、原件保存、内容去重、请求内解析、
   结构分块、状态持久化、手动重试与原件/内容/片段查看。详细范围见 `MVP.md`。
2. **检索**：已实现中英文关键词片段搜索、分页和来源块跳转。后续加入 PostgreSQL + pgvector、关键词与向量混合检索。
   用真实中英文资料评测后决定解析器、embedding、分词与 reranker。
3. **阅读与问答**：PC 原文阅读面板、流式回答、可定位且持久化的引用、会话管理。
4. **外部数据与上线**：cardless 只读接口、解析与问答费用、备份恢复、完整链路验收。

新 API 通过 `api/deps.py` 的 `require_owner` 保护，业务层无需接收 user_id。
数据模型应围绕 documents、chunks、conversations、messages 等实际实体演进；
第一版不建立独立 jobs 表或任务调度体系。
模型解析结果和索引属于可再生数据；原件及用户维护的资料信息需要独立保留。

## 第一版 MVP 的执行方式

- 第一版范围已确认缩减为：保存原件 → 解析 → 保存内容块 → 分块 → 保存片段 → 返回结果。
  不包含向量生成、检索或问答；`ready` 仅表示解析分块成功。单份文档的处理步骤串行执行。
- 这里的“单线程”指业务处理流程简单、顺序执行；不要求把 Web 服务的所有请求锁在同一个线程。
  不使用进程内后台任务来代替 worker，前端等待本次请求完成。
- 文档记录保留 processing、ready、failed 状态及失败阶段和错误信息。
  原件先持久化；处理失败后保留原件，支持手动重试，不做自动重试或断点续跑。
  服务重启后需识别中断的 processing 记录并允许手动重试，不自动恢复处理。
- 重试不重复创建片段；片段写入与成功状态通过同一事务提交。
- 已调整 nginx 的文件大小限制和请求超时，并设置逐页解析软预算与 OCR 子进程超时。
  MVP 接受处理期间等待请求的体验，先针对小规模文件验证完整链路。
- 处理逻辑保留清晰的函数边界；未来确有批量导入、长耗时处理或自动恢复需求时，再引入 worker。
- 分块目前采用明确的字符预算（1600 / 2400 / 200），不是 token 计数。
  选定 embedding 后再引入对应 tokenizer 并用真实资料评测参数。

## 迁移原则

不要为“删代码”执行 DROP TABLE、清理原文件或删除存储卷。
从旧库迁移时，先确认原件、旧记录与用户归属，建立明确映射，再重建片段索引。
旧数据库中的账户不会自动变成新系统访问者；访问权只由主人配置决定。
