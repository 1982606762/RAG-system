# 从中英丹搜索理解查询扩展与去重分页

这次问题不是资料没有保存，而是查询与原文的语言不同：中文“车贷利息”不会字面匹配英文 `loan interest` 或丹麦语 `renteomkostninger`。本次把查询扩展成三种语言的短检索词，再回到真实文档查找。

已核对你的《Django ORM：filter、关联查询与 Q 对象》：已有 AND、OR 和关联查询去重的基础；这里补充跨语言变体、分页顺序，以及缓存对象的区别。

## 是什么，为什么需要

**查询扩展**是在不改变问题意图的前提下，生成其他语言、同义词或常见词形的检索表达。它帮助“同一个意思，不同写法”的内容进入候选结果。

本次 `search/expansion.py` 让现有 Gemini 返回 `zh/en/da` 三组词，每组 1–3 个短变体。模型只收到搜索词，不收到本次搜索的文档正文；服务端检查结构、长度和词数，再交给数据库。Function calling 提供结构化参数，但仍需要应用校验，不能把模型输出当作可信代码。结构合法也不保证翻译语义正确；原始专名和标识符可以保留在外语变体中，不能仅凭含汉字就判定整条未翻译。[Google：Function calling](https://cloud.google.com/vertex-ai/generative-ai/docs/multimodal/function-calling)

这里通常是一轮查询扩展，加一个合并所有变体的 SQL 查询；不是为三种语言各启动一个并发搜索任务。命中查询计划缓存时，可以省去扩展调用。

## 如何使用：变体之间 OR，变体内部 AND

假设扩展结果为：

```python
queries = {
    'zh': ['车贷 利息'],
    'en': ['loan interest', 'total interest'],
    'da': ['billån renter', 'renteomkostninger'],
}
```

整体条件应理解为：

```text
(包含“车贷” AND 包含“利息”)
OR (包含“loan” AND 包含“interest”)
OR (包含“total” AND 包含“interest”)
OR (包含“billån” AND 包含“renter”)
OR 包含“renteomkostninger”
```

把不同语言全部用 AND 连接，会要求同一片段同时出现中英丹文字，反而容易零命中。把一组中的每个词全部 OR 连接，又会让只出现 `total` 的无关片段混进来。

`search/service.py` 还保留原查询作为一个可用变体，避免翻译丢失原文写法或型号。`search_chunk_variants()` 用参数化数组传入变体，以 `strpos(lower(...), lower(...))` 做字面子串匹配；它不是语言学分词或全文检索系统。

## 为什么先合并去重，再分页

一个英文片段可能同时命中 `loan interest` 和 `total interest`。如果每个变体各取一页，再拼接去重，会出现“一页不足额”“重复占位置”或跨页重复。

当前 SQL 对每个原始 chunk 使用 `LATERAL`，检查所有变体，再通过 `max(...)` 汇成一个匹配结果。无任何变体匹配时聚合值为 `NULL`，被过滤；匹配一个或多个变体时，仍只保留该 chunk 的一行。`LATERAL` 允许子查询引用当前外层片段。[PostgreSQL 16：LATERAL](https://www.postgresql.org/docs/16/queries-table-expressions.html#QUERIES-LATERAL)

随后才按“完整短语命中优先 → 文档创建时间 → 文档 ID → chunk 序号”排序，最后应用 `LIMIT/OFFSET`。后两个字段用于打破并列，形成可预测的顺序。稳定排序是分页的前提，但不是跨请求的数据快照：翻页间新增或修改资料，offset 结果仍可能移动。[PostgreSQL 16：LIMIT/OFFSET](https://www.postgresql.org/docs/16/queries-limit.html)

新增数据库集成测试用三种语言的合成资料、每页一条结果，检查三份文件都能找到、英文多变体不制造重复、失败文档不进入结果，以及指定文档范围不被扩展搜索突破。

## 查询词、搜索结果与引用，各有边界

| 对象 | 当前处理 | 原因 |
| --- | --- | --- |
| 查询计划 | 进程内最多 64 项，缓存 10 分钟；键含模型配置与原查询 | 减少重复翻译和短时间内的变体漂移 |
| 搜索结果 | 每次重新执行 SQL | 新上传资料不应被旧结果缓存挡住 |
| 引用证据 | 保留原 chunk、文档 ID 和来源位置 | 翻译词只是寻找证据的线索，不能成为证据 |

中文问答复用这套扩展。语义模式再合并语义命中，按 `(document_id, chunk_index)` 去重，不把同一来源分配成多份证据。前端展示实际检索词，方便检查扩展是否偏题。

扩展失败时，搜索 API 明确报错，用户可改用不调用 Gemini 的精确关键词模式。问答工具则带上 `multilingual_error`，继续尝试已有可用检索；“某种检索失败”和“资料不存在”必须分开。
