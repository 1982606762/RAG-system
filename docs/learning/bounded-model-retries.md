# 从一次问答失败理解有限重试

本次截图显示通用错误，生产日志只留下问答接口的 `503`。随后基础模型探测成功；经你许可，原问题也在约 6 秒内返回了带引用的答案。它说明故障没有持续复现，不能倒推当时一定是 Gemini 限流、过载或某一种具体故障。后补的错误日志只能帮助诊断今后的失败。

已阅读你的《数据导入：幂等、事务与版本留存》：其中覆盖稳定 ID、唯一约束与事务，但没有讨论网络退避和总时间预算；《Nexus G1 - Concurrent Log Fetching with ZMQ》也把 timeout、retry 列为待补内容。这次适合补上“重试可以恢复什么、又必须在哪里停止”。

## 是什么：失败后有条件地再试，而不是重新执行一切

临时错误可能在稍后恢复。**退避**是在重试前等待；**指数退避**让等待逐次增加；**jitter** 加一点随机时间，减少多个客户端同时再次冲击服务。

本次 `app/answers/provider.py` 对 HTTP `429、500、502、503、504` 重试，等待约 1 秒、2 秒，各加 0–0.25 秒随机量。`400` 参数错误、`401/403` 认证权限错误和 `404` 配置问题不走这段自动重试。Google 官方建议对临时故障限制重试次数并逐次延长等待；改变请求或配置才能解决的错误不应盲目重试。[API 错误说明](https://cloud.google.com/vertex-ai/generative-ai/docs/model-reference/api-errors)、[重试策略](https://cloud.google.com/vertex-ai/generative-ai/docs/retry-strategy)

## 为什么需要：吸收短暂波动，也保护等待时间与费用

旧逻辑遇到一次模型服务失败就结束问答。新逻辑给短暂故障恢复的机会，但重试并不保证成功，也不是免费操作。

这里有两个独立上限：

| 上限 | 当前实现 |
| --- | --- |
| 重试预算 | 一道问题的所有模型工具轮次，共享最多 2 次额外 HTTP 重试 |
| 时间预算 | 使用同一个 `deadline`，每次调用前重新计算剩余时间 |

**两次额外重试不等于整题最多三次模型调用。** 正常的检索、阅读、提交答案本来就可能需要多轮模型调用；只有因临时 HTTP 错误增加的尝试，才消耗 `self.retries`。

如果每轮都重新给两次重试，一道问题会被多次延长。当前 `Gemini` 实例在整道问题中复用，因而预算不会随工具轮次重置。

## 如何使用：先检查错误，再检查是否还值得等待

下面是当前逻辑的核心片段，省略 HTTP 收发和最终错误分类；`retries` 属于整题复用的模型对象：

```python
remaining = deadline - time.monotonic()
if remaining <= 0:
    raise TimeoutError()

# response = post(..., timeout=min(18, remaining),
#                 max_allowed_time=remaining)
if response.status_code in {429, 500, 502, 503, 504}:
    delay = 2 ** retries + random.uniform(0, .25)
    if retries >= 2 or deadline - time.monotonic() <= delay + 1:
        raise TemporaryFailure()  # 示意：转成明确的业务错误
    retries += 1
    response.close()
    time.sleep(delay)
    # 回到循环顶部，重新计算 remaining
```

`time.monotonic()` 适合测量经过时间，避免系统时钟校准影响预算。等待后重新计算剩余时间，不能把原始超时重新发给每次尝试。剩余时间连“等待＋至少一点执行空间”都不够时，直接停止。普通网络 timeout 也不应被理解为可强制抢占整个业务线程的精确硬截止。

当前代码只对列出的 HTTP 状态自动重试；网络异常、认证异常及客户端 timeout 仍直接分类报错，没有因为这次修改变成全部自动重试。

## 幂等与日志：恢复体验不能制造第二份业务结果

重试放在模型 HTTP 传输层，没有把“检索、生成、保存会话”整条流程重新运行。前端手动点击“重试”时，同一问题、深度及父消息仍复用原 `request_id`；后端能认出已经保存的轮次并返回原结果。

这与记账导入的稳定 ID 原理相通，但边界不同：**保存结果不重复，不等于外部模型推理绝不会重复执行或计费。** 请求响应丢失时，服务方可能已经完成推理；未保存成功的尝试再次运行，也可能再次消耗模型资源。Google 同样提醒不要无条件重试有副作用的操作。[重试策略的误区](https://cloud.google.com/vertex-ai/generative-ai/docs/retry-strategy#best_practices_and_anti-patterns)

本次还把限流、模型不可用、答案格式异常、会话存储错误映射到不同提示，并保留草稿。API 日志记录路由、状态和错误码；模型日志记录 HTTP 状态与重试次数。数据库异常另记异常类型，不把问题、检索正文或模型答案写入日志。这能缩小下一次排查范围，同时减少不必要的私人资料留存。

## 何时使用、学习范围与自测

适合采用有限重试的场景，是明确可能恢复的短暂上游失败。持续配额不足需要检查配额或调用方式；权限、参数、模型名称错误需要修配置。转账、创建订单等写操作不能直接套用这段循环，需要先确认幂等协议。

现在先掌握：区分可重试错误、次数与总时间分别设限、重试层级影响副作用、日志不能证明未记录的历史原因。以后再深入 `Retry-After`、熔断、多层 SDK 重试叠加和分布式追踪。新增依赖或换 SDK 时，要检查底层是否已有重试，避免预算被叠乘。

1. 第一轮模型请求已经用掉一次重试，第二轮连续收到两个 `503`。还会进行第三次尝试吗？为什么？
2. 服务端已保存答案，但浏览器没有收到响应。保留同一个 `request_id` 解决了什么？它为何不能保证模型费用只发生一次？
